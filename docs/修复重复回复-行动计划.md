## 1. 问题概述

### 1.1 现象

通过 IRC 频道 `#xia` 发送一条消息，bot（`deepseek_ai`）回复了 **3~5 次**。

### 1.2 根因（最终确认）

**根因 1：多个插件实例同时运行**

DSH autoload 框架多次加载插件（每次 `apply()` 创建一个 `ctx.interval`），但旧 interval 未被 Cordis 销毁。多个 interval 同时读取 inbox 并调用 `followup`，导致同一条消息被注入 agent 多次。

**根因 2：全局 seq 去重失效**

`agent.session.events` 返回**全局事件**（含其它会话），seq 号全局递增。irc-xia 的 `assistant/message` 事件 seq 远小于全局最大 seq，被 `lastProcessedSeq` 跳过。

**根因 3：agent status 卡住**

agent 完成 turn（session 有 `turn/end`）后，`ircAgent.status` 仍为 `'running'` 而非 `'idle'`，导致插件不调用 `followup`，后续消息不被处理。

## 2. 修复内容

### 2.1 消息 ID 去重（`processedMsgIds`）— ✅ 已实现

替代全局 seq 去重。按 `assistant/message` 的唯一 `msg.id` 去重，避免全局 seq 不匹配问题。持久化到 `processed-msg-ids.json`。

### 2.2 文件锁（`LOCK_FILE`，3600s 超时）— ✅ 已实现

防止多个插件实例同时创建 interval。若锁文件存在且 < 3600 秒，新实例跳过 interval 创建。pollInbox 每次执行刷新锁时间戳（保持锁不过期）。

### 2.3 入站去重（`sentInboxTs`）— ✅ 已实现

同一入站消息（同 `ts`）只 `followup` 一次。

### 2.4 500ms 窗口（`lastFollowupTime`）— ✅ 已实现

防极快连续 poll 重复发送。

### 2.5 IRC 发言累积限速（rate-limiting）— ✅ 已实现

**目的**：防止 AI 在聊天室持续不断发言，同时允许用户粘贴多行数据时不被打断。

**规则**：
- 每个 sender 初始需要 **1 条消息**即发送
- 每次发送后，该 sender 的阈值增加为 `原阈值 + 本次实际累积数`
- 5 分钟无该 sender 发言 → 仅重置 `required=1`，**不释放** `waitingBuffers` 和 `accumulated`
- 未达阈值的消息暂存到 `waitingBuffers[sender]`，**不会**被其他 sender 的达标消息触发发送
- 达标时合并 `waitingBuffers[sender]` + 本次新消息一起发送
- 冷却后该 sender 再发任意条新消息 → `accumulated ≥ 1 = required` → 立即合并发送（旧暂存 + 新消息）

**示例流程**：
| 轮次 | A累计 | required | accumulated | 是否发送 | waitingBuffers | next_required |
|------|-------|----------|-------------|---------|----------------|---------------|
| 1    | 1条   | 1        | 1           | ✅      | —              | 2             |
| 2    | 3条   | 2        | 3           | ✅      | —              | 5             |
| 3    | 4条   | 5        | 4           | ❌      | 'msg1\nmsg2\n...'（暂存） | —          |
| **冷却后**A发1条 | 1条 | **1**(重置) | **1** | ✅ | 合并发送(waitingBuffers+A新消息→全部6条) | **2** |

**关键行为（冷却后 waitingBuffers 保留）**：第3轮 A 发了4条但 required=5，未达标 → waitingBuffers['A'] 暂存。第4轮冷却触发（5分钟无发言），required重置为1。**waitingBuffers 不清空**。此时 A 再发任意新消息（≥1条）→ accumulated ≥ required=1 → 立即合并发送旧暂存 + 新消息。

**实现位置**：`host.js` pollInbox → `senderRequired`, `senderAccumulated`, `senderLastSendTime`, `waitingBuffers`

### 2.6 sentTexts 去重移除 — ✅ 已修复

## 3. ✅ 已解决：agent status 卡住（P0 修复）

### 3.1 现象

agent 完成 turn（session 有 `turn/end`，reason='completed'），但 `ircAgent.status` 仍为 `'running'`。插件检查 `ircAgent.status === 'idle'` 失败，不调用 `followup`，后续消息不被处理。

### 3.2 根因

DSH agent 生命周期 bug：`turn/end` 后 agent 的 `status` 属性未从 `'running'` 更新为 `'idle'`。这是 DSH 核心问题，非插件问题。

### 3.3 P0 修复（已实现并验证）

**方案**：不依赖 `ircAgent.status`，改用 session 事件判断 agent 是否空闲。

**实现**：新增 `isAgentIdle()` 函数替代 `ircAgent.status === 'idle'` 检查：

```js
function isAgentIdle() {
  try {
    const events = ircAgent.session.events
    if (!Array.isArray(events) || !events.length) return true // 无事件 = 空闲
    const lastEv = events[events.length - 1]
    if (lastEv && lastEv.type === 'turn/end') return true // turn/end = 空闲
    const hasMessage = events.some(e => e && e.type === 'assistant/message')
    return !!hasMessage // 有回复但无 turn/end → 也允许发送
  } catch (e) {
    return false
  }
}
```

同时为 `followup()` 添加 try/catch 错误处理。

|------|---------|---------|------|
| P0 测试1 | "P0测试：agent空闲检测修复" | ✅ 收到回复 | 通过 |
| P0 测试2 | "P0测试2：确认followup触发" | ✅ 收到回复 | 通过 |
| 端到端测试 | "最终端到端测试：P0修复已确认生效" | ✅ "收到，P0 修复已确认生效。" | **通过** |

**结论**：agent-stuck 问题已修复。`isAgentIdle()` 正确检测 agent 空闲状态，`followup()` 正常调用，agent 处理消息并生成回复。

### 3.5 遗留问题：重复回复（需 DSH 重启）

**根因**：autoload 框架在 DSH 运行期间多次加载插件（间隔约 20 分钟），每次加载创建新 interval。旧锁 3600s 超时足够长，pollInbox 刷新锁保持活跃实例不重复创建。

**修复**：
1. 锁超时从 300s 增加到 3600s（1 小时）
2. pollInbox 每次执行刷新锁时间戳（保持锁不过期）
3. IRC bot drainOutbox 改用原子 rename 避免与插件 outbox 写入竞态

**验证**：DSH 重启 + 新 interval 创建后，连续两次端到端测试均通过（1 message → 1 reply）✅

## 5. 重要教训

### 5.1 不要在 sessions 目录留备份

把 `irc-xia/` 改名为 `irc-xia.bak-XXX/` 留在 sessions 目录 → DSH 启动崩溃（`assertStoredIdentity` 校验失败）。

**正确做法**：`rm -rf` 删除，如需备份移到 sessions 目录外。

### 5.2 cordis_define 大代码

`cordis_define` 可处理 ~18k 字符代码（非之前以为的 4k 限制）。之前失败是 JSON 转义问题。

### 5.3 ctx.effect 会清空锁文件

`ctx.effect` 在插件被 autoload 重新加载时触发，清空了锁文件。移除 `ctx.effect` 后锁正常工作。

### 5.4 锁是"加载时一次性检查"，无法感知持锁实例死亡

插件只在 `apply()` 时检查一次锁文件。若持锁实例崩溃/退出但未清理锁，且锁时间戳仍在 3600s 内，新实例会误判"已有实例在运行"而跳过 interval，**之后不再重查** → 永久停止轮询。

**缓解**：
- 故障时手动 `rm plugin.lock` + 重启 DSH
- 长期方案：interval 内定期重查锁（当前 pollInbox 只刷新锁，不重新判断归属）
